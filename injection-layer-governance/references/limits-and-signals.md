# 上限速查 · 信号对照 · 开关

> 本文件是 `injection-layer-governance` 的数据附录。**所有数字都是"字符数"（`wc -m` 等价口径）**。
> 上限值来自一次源码级实测，**随客户端版本可能变化**：升级客户端后，或发现实际行为与本表不符时，
> 走**机制级取证**（直接读客户端的源码 / 资源包）重测后再更新这里 —— **不要凭印象改数**。

---

## 1. 上限速查

| 槽 | 源路径（按平台约定） | 上限 | 超限行为 | 能自己改吗 |
|---|---|---|---|---|
| 工作记忆 | `<项目>/.workbuddy/memory/MEMORY.md` | 8000 | 截断 + 追加清理强指令 | ✅ |
| 用户记忆 | `~/.workbuddy/MEMORY.md` | 4000 | 截断 | ✅ |
| 云档案 | 云端归档（本地有缓存副本） | 10000 | 截断 | ❌ 平台侧 |
| 项目说明 | `<项目>/CODEBUDDY.md`、`.codebuddy/CODEBUDDY.md`、`AGENTS.md` | 8000 | 省略 | ✅（槽常为空） |
| 项目规则 | `~/.workbuddy/rules/`、`<项目>/.codebuddy/rules/` | 40000 **每文件** | **整条丢弃** | ✅ |
| 个人指令 | 设置界面 → 个人指令（配置项） | 1500 | **静默丢弃** | ✅ **但必须走 UI** |
| 身份三件套 | `~/.workbuddy/SOUL.md` / `IDENTITY.md` / `USER.md` | 10000 **每件** | 截断 | ✅ |
| 目录清单 | 自动扫项目根目录（**非隐藏**条目） | 40 条 / 6 层 / 5 后缀 | 第 41 条起完全不可见 | 🟡 改结构 |
| 交接件（HANDOFF 等） | — | — | **不注入**，无槽位 | — |

**两条易错**：
- **项目说明是"首个命中即停"**：三个候选路径里只有一个会被读，三个都放等于只有第一个生效。
- **规则是"每文件"上限，不是总量上限**：写 10 个文件、每个 39999 字符会全部注入（总量 40 万）。所以**拆成多个文件**本身就是一种扩容手段 —— 代价是占用上下文。

## 2. 超限行为四档（严重度递增）

```
① 截断              丢尾部，模型看到的比你写的少
② 截断 + 追加强指令   丢尾部，且平台追加一段"立即清理"的指令 —— agent 一开局就被派了活
③ 静默丢弃          超出的部分连写都没写进去，无任何报错  ← 最阴
④ 整条丢弃          整个文件被忽略，等于白写
```

**判定方法**：
- ①②④ → 去注入块里找截断标记（见下节）。
- ③ → **只能靠字符计数**。判据：**界面上的计数 == 你预期的长度**。计数小于预期就是被吞了。
- **不要去问"有没有报错"** —— ③④ 都不报错。

## 3. 截断标记 → 归因对照

在自己的上下文里看到下列片段时，直接对号入座，**不要猜**：

| 标记片段 | 来自哪一层 | 说明 |
|---|---|---|
| `memory truncated — MEMORY.md is too large` + `ACTION REQUIRED` | 项目级工作记忆 | 超 8000，**并且平台追加了清理指令** |
| `(user memory truncated)` | 本地用户记忆 | 超 4000 |
| `(user memory truncated — exceeded character limit)` | 云档案 | 超 10000（与上一条**长得很像，但不是一个东西**） |
| `(binary context truncated …)` | 二进制环境信息 | 超 10000，**不属于用户资产，别治** |
| `[too long, omitted]` | 项目说明 | 超 8000 |

> **技巧（零成本的自检）**：每个会话开局，看一眼自己上下文里被注入的块 ——
> 凡是**尾部出现了被腰斩的单词/半句话**，就是那一层被截断了。
> 这个观察**不需要跑任何工具**，应该是每轮开工的第一手校验。

## 4. 各槽的"源"怎么定位

判断"某个对象在不在注入路径上"，**看它是否落在上表的源路径**；不要因为它"在磁盘上存在"就认定它会被注入。

容易混的一类：**某个项目会有一个"仓库根目录下也放着一份 `MEMORY.md`"**的写法 —— 那个文件**不是**注入对象（注入只认 `<项目>/.workbuddy/memory/MEMORY.md`）。
> 曾因此把一个 3 万字符的非注入文件报成"正在被截断"，错误结论扩散到了 7 份文档。**教训：先证明路径，再声称注入。**

## 5. 开关（用之前先想清代价）

平台可能提供"关掉某层记忆"的开关。**它们不是治理手段，是手术刀**：

| 想关的层 | 大致效果 | 代价 |
|---|---|---|
| 本地记忆（含项目级 + 用户级） | 这几层全部注入为空 | ⚠️ **等于放弃跨会话记忆** —— 不推荐，除非你有别的持久化通道 |
| 云档案 | 跳过云档案注入 | 只关最外层；本地各层仍注入。**是否是你要的效果要先确认** |

**用开关前必做三件事**：
1. 确认这个开关**真的存在**且**语义是你以为的那个**（同名的东西可能属于完全不同的子系统，比如"内存"与"记忆"）。
2. 确认它能被本地设置生效 —— 有些开关由云端下发，本地改不动。
3. 想清楚**关掉之后靠什么补**。

> 本 skill 的默认立场：**优先"拆 + 外移"，而不是"关掉"**。关是最后手段。

## 6. 收口判据：怎么知道"探完了"

不要用"感觉差不多了"收口，也不要陷入"总能再挖一点"的死循环。判据有两条：

1. **多源穷举**：注入面至少有**三个源** —— ① 磁盘上的模板文件、② 程序内的代码拼接、③ 运行时动态生成。**只搜其中一个源，会把"我在 A 里没搜到"误判成"平台没有"。** 实例：有些注入块标签只存在于 ①，有些只在 ② —— 单源搜索必然漏。
2. **观测集全覆盖**：把你**自己上下文里实际存在的每一个注入块**逐个回查生产点，**全部可追溯**才算收口。这比"再搜几个关键词"可靠得多。

**收口之后问的不是"还有没有新发现"，而是"新发现会不会改变方案骨架"**：
- 只改变"哪些对象适用哪条手段" → **骨架已稳定，冻结，转执行**。
- 改变"手段清单"本身 → 才需要重开。

还有一类**结构上不可穷举**的东西要单独识别：**模型的注意力可靠性**。它不能靠"再探"或"换个地方放"解决，**只能机制化（脚本 / 门禁）**。

## 7. 版本升级后的复核清单

客户端升级后，按顺序核这几项（走机制级取证：读客户端源码 / 资源包）：

- [ ] 各上限常量**是否变了**（尤其是你正好贴着上限的那几层）
- [ ] **槽位清单**是否增减（有没有新增的注入块）
- [ ] **截断标记文案**是否改了（改了的话本文件第 3 节要同步）
- [ ] **配置文件写入路径**是否改了（关系到红线第 1 条）

> 复核完把本文件的数字更新掉，并**注明测于哪个版本**。没测就别改。
