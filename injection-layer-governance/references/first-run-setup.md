# 首装：从三件套到军规，再到治理规则

> **一句话**：新机器（或新容器）第一次配注入层，按「**人是谁 → 纪律是什么 → 怎么维护自己**」三步写完 ——
> 这台机器的会话开局就已经带着这三样东西，而不是等哪天想起来了再补。
>
> 本节是**写内容**；把**已有**内容搬过来是迁移，见 `playbook.md` §3。主流程（体检 → 判定 → 治理 → 验收）见 `SKILL.md` §3。
> ⚠️ 本文件里的机制结论测于某个客户端版本；升级后按 `limits-and-signals.md` §7 复核。

---

## 0. 先判走哪条路（三条路不能混）

判据一句话：**这段话换到这台机器上还成立吗？**

| 情形 | 走哪条 | 动作 |
|---|---|---|
| 新机器，源机**已有全套**且内容原样可带走 | **迁移** | 搬文件，**不重写内容** → `playbook.md` §3 |
| 新机器 / 新容器，**什么都没有** | **首装** | 按本文件 1 → 3 步写 |
| 源机有内容，但**本机语境不同** | **三件套重写 + 其余迁移** | 三件套按 §1 重写；军规、治理规则、skills 可搬 |

### 0.1 一条顺序硬约束（做反了要手工合并）

**先写文件，再让客户端跑第一次会话。**

平台的初始化写入是「**只补缺、不覆盖**」式的：文件已存在，平台一字不动；文件不存在，平台生成一份默认模板占位。

- **先写 → 平台认**（源码级结论：初始化走的是「缺则写」的路径）。
- **先让平台生成 → 再写**：文件在盘上被更新是确定的；**但是否在下一个会话就注入，本文件不做假设** —— 按 §4 第 4 条**动态验证**去确认（`--session` 模式直接读注入块，比肉眼看上下文可靠）。

**顺带一个免费信号**：三件套内容 ≠ 默认模板时，平台**直接记为「已完成引导」**，不再来问一轮「你是谁」。

## 1. 第一步 · 三件套（人是谁）

装的是**稳定内核**，不是工作法。工作法放规则或 skill。

| 文件 | 装什么 | 目标体量 | 不装什么 |
|---|---|---|---|
| `SOUL.md` | 人格内核 + 行为边界 + 连续性约定 | 700–1500 | 工作流程、项目信息、待办 |
| `IDENTITY.md` | 助手是谁：名字 / 定位 / 角色 / 边界 / 搭档 | 300–900 | 履历细节、技术栈清单 |
| `USER.md` | 用户是谁：称呼 / 身份 / 交付判据 / 配合方式 / 环境 | 600–1500 | 项目进展、一次性结论 |

上限 **10000 字符／件** ⇒ 目标体量都留了 ≥85% 余量，是为了「以后还能往里加」。

**填空模板**：`assets/first-run/SOUL.template.md` / `IDENTITY.template.md` / `USER.template.md`（骨架已搭好，把 `«»` 换成自己的话）。

⛔ **明文要求（这一条别省）**：**不要把别台机器的三件套整份拷过来。**

三件套写的是「**这台机器上的人是谁**」。机器名、账号、常驻项目、协作对象都可能不同 ——
整份复制的结果是：这台机器一边自称别人，一边按别人的判据干活。

**正确做法**：拿骨架，用自己的话把每一节重写一遍；只有真正跨机不变的部分（比如称呼）才原样保留。
**逐节自检一句**：「这一节换到这台机器上，还成立吗？」不成立 → 重写。

## 2. 第二步 · 军规（纪律是什么）

**放哪**：

| 层 | 位置 | 生效范围 | 跨机 |
|---|---|---|---|
| 用户级 | `~/.workbuddy/rules/` | **全部项目** | **机器本地** ⇒ 换机必须手工搬 |
| 项目级 | `<项目>/.codebuddy/rules/` | 该项目 | 随项目走 |

**四条硬约束**（违反会**静默失效**）：

1. 只认 `.md` / `.mdc`。
2. 裸 `.md` 默认**总是应用**；带 `paths` 的**条件规则当前不注入** —— 关键纪律不要写成条件规则。
3. 单文件上限 **40000 字符**；超限**整条丢弃**（不截断、不报错、等于白写）。
4. 注入顺序：**用户级先、项目级后**（后者语义更强）。

**该装什么**：这个槽的语义是「**当作用户亲口说的来遵循**」⇒ 装**行为纪律** —— 怎么做事的硬要求。

⛔ 不装：项目情况（→ 项目说明）、知识/结论（→ 记忆或文档）、说话习惯（→ 个人指令）。
判「这句话该放哪个文件」用 `SKILL.md` §4 的四槽归位表。

**装完自检**：

```
python3 scripts/scan_injection_surface.py --only rules
```

## 3. 第三步 · 治理自律规则（怎么维护自己）

前两步装的是「人」和「纪律」；这一步装的是**让这台机器不让自己的记忆越线**的那条规矩。

现成的可直接落位：`assets/first-run/rules/09-injection-layer-discipline.md`
（文件名用 ASCII 是为了跨平台不乱码；**落位时可改成本机 `rules/` 目录的编号风格**，文件名不影响内容。）

> 它是完整方法的**压缩版** —— 规则每轮都在场，所以只留判据与动作；完整方法在本 skill 里，按需读。
> ⚠️ **落位前按本机实际核一遍上限值**：上限是客户端版本的函数（`limits-and-signals.md` §1）。

## 4. 第四步 · 验收（三静态 + 一动态 + 负控制）

| # | 信号 | 怎么验 | 期望 |
|---|---|---|---|
| 1 | 体量合规 | 跑体检脚本 | 新增对象全部 ≤ 上限 |
| 2 | 真是自己写的 | 拿默认模板的特征串当探针（模板标题、模板里的英文句） | **0 命中** |
| 3 | 落位正确 | 逐文件核对源路径（`rules/` 只认 `.md`；三件套在配置目录根） | 逐个存在 |
| 4 | **动态** | 跑 `scan_injection_surface.py --session --cwd <容器>`，看注入块逐槽是否＝磁盘当前内容 | 逐块能对上文件 |
| 5 | 负控制 | 在临时目录造一个**假越线对象**（灌到 > 上限） | 脚本**必须报红** |

**第 4 条要「改动之后启动」的会话才作数**：静态（文件内容 + 字符数）随时可证；动态读的是**会话开场注入块**——
它原文落盘在 `projects/<slug>/<uuid>.jsonl` 的开头几条记录里，用 `--session` 模式直接读，不必靠肉眼翻上下文。
手头没有改动之后启动的会话 ⇒ 如实写「待新会话验证」，**别写成已验证**（那就成了只能绿不能红的假绿）。

**边界（别越界声称）**：可证的是 身份 / 规则 / 项目说明 / 目录 / customPrompt；
**工作记忆与云 profile 不走这个块**（走系统提示、不落盘）⇒ 这两者的「是否被注入」此法证不了。

**第 4 条怎么读结果（含两个反直觉点）**：

0. **脚本按「会话起点」选最新会话，不按「最后写入时间」。** 别用 mtime 挑会话：你就在某个会话里跑脚本时，
   那个会话自己一直在被追加写入、永远赢 mtime 竞争 ⇒ 会拿到「你正坐着的这场」而不是「新开的那场」。
   脚本会打印**会话起点**（判「能不能验到你的改动」看它）＋**末次写入**，并列同容器其它会话供 `--session-file` 点名。
1. **在改文件的同一个会话里看注入块，它仍然是旧内容** —— 这是**正常的**，不是失败。
   注入块是**会话开局快照**，同一个会话内不刷新（这就是「注入 ≠ 常驻」）。
2. 开一个**新会话**再看。变了 → 通过。
3. **仍是旧的** → 完全退出客户端再启动，开新会话重看。
4. **还是旧的** → 这时才按「读一次即缓存」的假设做机制级取证，**不要反复重试**。
